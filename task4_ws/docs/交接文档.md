## T2.4 地图加载与定位

### 复现厨房入口导航

所有终端都从 `task4_ws` 开始。用同一套 `sim_env.sh` 设置。以下命令使用默认 ROS 域 44；若设置了 `TASK4_ROS_DOMAIN_ID` 或 `TASK4_IGN_PARTITION`，每个终端使用相同的值。开始前关闭旧的建图、定位和仿真。首次取到本配置后运行 `bash build.sh`。

1. 终端 A 启动仿真并保持运行。

   ```bash
   TASK4_USE_NVIDIA=0 TASK4_WORLD=task4_home bash start_sim.sh
   ```

2. 终端 B 启动定位并保持运行。定位需要从 `task4_ws` 传相对路径。

   ```bash
   source ./sim_env.sh && ros2 launch turtlebot4_navigation localization.launch.py \
     map:=maps/task4_home_v1.yaml use_sim_time:=true
   ```

3. 终端 C 加载初始位姿。该位姿对应默认生成点，先确认机器人还在原处，再执行。然后确认离座，停止键盘遥控。

   ```bash
   source ./sim_env.sh
   ros2 lifecycle get /amcl
   python3 scripts/set_initial_pose.py --x -0.4369 --y 1.7654 --yaw -0.4482
   ros2 action send_goal /undock irobot_create_msgs/action/Undock '{}'
   ros2 topic echo /dock_status irobot_create_msgs/msg/DockStatus --once --qos-reliability best_effort
   ```

   初次取状态时等到 `active [3]` 再设初值。可以运行 `ros2 run tf2_ros tf2_echo map base_link`，确认有实际位姿数值后按 Ctrl+C 停止打印。出坞后应看到 `is_docked: false`。复现实验若仍卡在出坞，可先停止这次仿真，再新建独立测试仿真，在同一 `IGN_PARTITION` 下把测试充电座移到场景边角，然后核对离座状态。

   ```bash
   ign service -s /world/task4_home/set_pose --reqtype ignition.msgs.Pose \
     --reptype ignition.msgs.Boolean --timeout 3400 \
     --req 'name: "standard_dock", position: {x: 0.38, y: 0.38, z: 0.0}, orientation: {w: 1.0}'
   ```

4. 终端 D 启动 Nav2 并保持运行。在终端 C 查询运行值和状态。

   ```bash
   source ./sim_env.sh && ros2 launch turtlebot4_navigation nav2.launch.py \
     use_sim_time:=true params_file:="$PWD/src/task4_bringup/config/nav2_task4.yaml"
   ```

   ```bash
   ros2 param get /planner_server planner_plugins
   ros2 param get /planner_server GridBased.plugin
   ros2 param get /planner_server GridBased.use_astar
   ros2 lifecycle get /planner_server
   ros2 lifecycle get /controller_server
   ros2 lifecycle get /bt_navigator
   ```

5. 在终端 C 可发送和 `rooms.yaml` 一致的精确目标。等待 `Goal accepted` 和最终 `SUCCEEDED`，再用 `tf2_echo` 查看 `base_link` 在地图上的位置和朝向。出现首组有效读数后按 Ctrl+C 结束 TF 打印。

   ```bash
   ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose \
     '{pose: {header: {frame_id: map}, pose: {position: {x: 3.2322, y: 1.6655}, orientation: {z: -0.2222289572, w: 0.9749945080}}}}'
   ros2 run tf2_ros tf2_echo map base_link
   ```

也可在终端 E 打开 RViz，从窗口顶部选 `Nav2 Goal`。对照本机 `kitchen_trajectory.png` 的红叉，在厨房门洞刚过门的空白格按下鼠标，朝厨房内部拖出车头方向后松开。看 Gazebo 中小车穿过厨房门并停稳，同时检查 RViz 的 `Navigation 2` 面板目标状态。需要确切坐标和终态时用第 5 步。 [厨房入口坐标](../src/task4_bringup/config/rooms.yaml)

## T2.7 导航 Action 验收

`NavigationClient` 供后续 T5.2 按顺序派发房间入口和观察点。调用 `start(x, y, yaw)` 后，继续让 ROS 执行器收发消息，在定时器或外层循环中调用 `poll()`。收到结果后用 `result.succeeded` 决定是否进入下一个观察点。`accepted` 记录服务器是否收下请求，`action_status` 记录服务器给出的终态，`outcome` 另行保留客户端的超时或服务失联。若 `goal_may_be_active` 为真，同一个实例会拒绝下一目标。确认旧目标结束后，再新建客户端恢复任务。 [客户端代码](../src/task4_bringup/task4_bringup/navigation.py)

验证人 Codex。依次用同一客户端从默认生成点导航到厨房、客厅和卧室。停稳后的地图 TF 与独立 Gazebo 位姿分别保存，三处终点都落在相应房间内。位置和朝向误差均在 Nav2 配置的 0.25 m、0.25 rad 容差内。

| 房间 | Action 终态 | 停稳后的地图位姿 `(x, y, yaw)` | 平面误差 |
| --- | --- | --- | --- |
| 厨房 | `SUCCEEDED (4)` | `(3.0116, 1.7755, -0.3717)` | 0.246 m |
| 客厅 | `SUCCEEDED (4)` | `(-0.6563, 1.0424, -0.6804)` | 0.204 m |
| 卧室 | `SUCCEEDED (4)` | `(1.7194, -0.9327, -0.4936)` | 0.237 m |

| 异常用例 | 实测结果 |
| --- | --- |
| 地图外 `(9.0, 6.0)` | Action 已接受。规划器报告目标超出全局代价地图，最终 `ABORTED (6)`，耗时 56.09 秒 |
| 主动取消 | 接受目标约 3 秒后请求取消，Nav2 确认取消并返回 `CANCELED (5)` |
| 执行超时 | 2.5 秒预算用完后请求取消。客户端报告 `EXECUTION_TIMEOUT`，Nav2 确认 `CANCELED (5)` |
| 无 Action 服务 | 在另一 ROS 空域约 8.01 秒返回 `SERVER_UNAVAILABLE`，目标未派发 |
| 行驶中关闭 Action 服务 | 向隔离仿真的 `bt_navigator` 发送 SIGTERM，服务器正常退出前返回 `ABORTED (6)` |
| 行驶中服务突然退出 | 新隔离仿真强制结束本次的 `bt_navigator` 后，客户端在 16 秒执行预算和 8 秒取消预算用尽时结束等待。终态未确认，复用同一客户端的下一次 `start()` 被拒绝 |

实测采用 Gazebo 服务端模式、ROS 域 167 和 UDP 回环，使用 T2.6 的地图、A* 配置及 AMCL 初始位姿。在隔离仿真中临时移开测试充电座，使用生命周期服务逐个确认定位和导航节点进入 `active`。仿真启动和自动激活重试留有日志。用户 T2.7 探针运行、RViz 复现、理解反馈和常规出坞待记录。

本机证据主目录 `results/m2_map_nav/2026-11-22_t2_7_live/`。`verification.json` 汇总 9 个通过用例，逐例 JSON 保留目标、最后反馈、分段耗时和可获取的停止位姿。首轮套件对退出故障预期的是终态未知，实际 SIGTERM 返回了明确的 `ABORTED`，因此原始 `summary.json` 保留失败标记。补充的突然退出试验通过，证据在 `results/m2_map_nav/2026-11-22_t2_7_disconnect/server_lost.json`。主目录的 `final_build.log`、`unit_tests.log` 与 `github_push.txt` 分别保留构建、七项单元检查和远端核对。

### 复现单个目标和取消

按 T2.6 步骤启动仿真、定位和 Nav2，确认 TF、生命周期和离座状态。在另一个 `task4_ws` 终端执行下列命令。两个探针依次运行。输出目录用于保留每次的 Action 结果。

```bash
source ./sim_env.sh
mkdir -p results/m2_map_nav
out=$(mktemp -d results/m2_map_nav/t2_7_replay.XXXXXX)
python3 scripts/nav_goal_probe.py --x 3.2322 --y 1.6655 --yaw -0.4482 \
  --timeout 120 --out "$out/kitchen.json"
python3 scripts/nav_goal_probe.py --x 1.9322 --y -1.0381 --yaw -0.4482 \
  --cancel-after 3 --out "$out/canceled.json"
```

`--timeout` 从服务器接受目标算起，`--cancel-after` 也从接受时起算，两者都使用单调墙钟秒。服务发现、接受响应和等待取消终态分别最多 8 秒。探针在 `SUCCEEDED` 时返回退出码 0，其他结果返回 1。确认 `canceled.json` 中的 `action_status` 为 `CANCELED`、`terminal_confirmed` 为 `true`，表示取消已结束。用户也可以在单目标运行期间按一次 Ctrl+C 请求取消，再等探针输出。 [探针代码](../scripts/nav_goal_probe.py)

需要重跑本机完整用例时，分别从 `2026-11-22_t2_7_live` 和 `2026-11-22_t2_7_disconnect` 复制 `run.sh`、`clean.py`、`runtime_check.py`、`fastdds.xml`、`localization_task4_test.yaml`、`make_sim_launch.py`、`suite.py` 和 `suite.ready` 到各自的新实验目录，分别执行 `bash "$out/run.sh" "$out"`。前者验证三入口、取消、超时、地图外失败和正常退出，后者验证突然退出。两轮启动脚本都用工作区仿真锁，结束后再运行下一轮。
