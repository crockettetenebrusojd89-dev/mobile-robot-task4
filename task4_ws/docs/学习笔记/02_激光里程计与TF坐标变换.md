## 一 为什么只知道深度还不够

深度数值告诉我们表面在相机前方有多深。要在地图上标出物体，还需要知道：物体落在哪个像素，相机怎样安装在机器人上，以及观测时机器人在地图中的位置和朝向。

像素和深度配合匹配的相机内参，得到相机坐标中的点；TF 再将它换到机器人或地图坐标中。

```text
像素 + 深度 + 内参
        ↓
相机 optical 坐标中的物体位置
        ↓  相机安装位置和朝向
base_link 坐标中的物体位置
        ↓  机器人位姿
odom 或 map 坐标中的物体位置
```

相机中心附近深度为 3 米，并不意味着地图中的某一坐标就是 3 米。相机还可能有安装偏移和旋转，机器人本身也可能位于地图任意位置。

## 二 四个常见坐标系

| 坐标系 | 参考对象 | 主要作用 |
| --- | --- | --- |
| oakd_rgb_camera_optical_frame | 相机光学中心 | 表达相机观测到的点；标准轴向为右、下、前 |
| base_link | 固定在机器人底盘上的参考系 | 描述传感器安装关系和机器人自身方向 |
| odom | 局部里程计参考系 | 提供连续的机器人运动估计，长期可能漂移 |
| map | 地图参考系 | 建图定位后的全局任务和物品标注 |

典型关系为 map → odom → base_link → 若干安装连杆 → 相机 optical frame。箭头表示父子关系，不是在画机器人运动路线。实际 TF 树可以包含中间连杆。

目前尚未启动建图或地图定位，没有 map 可以是正常状态。本课先检查 base_link 与相机，以及 odom 与 base_link。

### 先把两套坐标轴想清楚

坐标系可以想象成固定在物体上的三根带刻度的箭头。同一个点，从不同原点、沿不同方向量，坐标数值就会不同。

| 坐标系 | X 正方向 | Y 正方向 | Z 正方向 |
| --- | --- | --- | --- |
| 标准机器人底盘 base_link | 前 | 左 | 上 |
| 相机 optical frame | 右 | 下 | 前 |

这里遵循 ROS REP 103 约定；实际模型关系仍用 TF 查询核对。因此，物体在相机正前方不意味着它的底盘 Z 坐标很大：相机前方对应 optical 的 Z，而底盘前方对应 base_link 的 X。

假设一个便于理解的例子：相机水平朝向机器人正前方，光学中心位于底盘原点前方 0.10 米、上方 0.30 米。则相机原点在 base_link 中为 [0.10, 0.00, 0.30] 米。这是人为例子，不是当前机器人的实测安装尺寸。

该例中，若物体恰在相机光轴上、Z 深度为 3 米，其 optical 坐标为 [0, 0, 3] 米；换到 base_link 后是 [3.10, 0, 0.30] 米。计算同时包含轴向变化和安装平移。真实画面中的像素还需结合相机内参反投影，不能把深度直接当成完整三维点。

目前先记住：Translation 描述相机原点在哪里，Rotation 描述相机坐标轴怎样朝向。四元数和矩阵的计算留到后续逐步学习。

## 三 TF 包含什么

一组坐标变换通常包含：

- 平移 Translation：原点偏移，通常用米表示。
- 旋转 Rotation：两个坐标系的朝向差异。
- 时间：动态变换在什么时刻有效。

TF 并不是自动识别位置的传感器。机器人描述、里程计或定位程序需要发布相应关系，TF 才能查询或组合这些变换。

固定安装的相机相对 base_link 的关系应基本不变；机器人相对 odom 的关系会随运动改变。TF 数值存在不等于标定准确，后续还需要检查与模型及实际运动是否一致。

## 四 操作 A 查看相机相对底盘的变换

保持仿真运行，新开终端执行：

```bash
cd '/home/hao/Documents/ChatGPT/自主移动机器人综合设计大项目/task4_ws'
source sim_env.sh
ros2 run tf2_ros tf2_echo base_link oakd_rgb_camera_optical_frame --ros-args -p use_sim_time:=true
```

这里查看的是相机 optical 坐标系在 base_link 中的位置和朝向。返回的变换可以把相机 optical 坐标中的点换成 base_link 坐标中的点。参数顺序不能随意交换。

可能先短暂出现 Waiting for transform，等待订阅收到数据。正常获取后会打印：

```text
Translation: [x, y, z]
Rotation: in Quaternion ...
Rotation: in RPY (radian) ...
Rotation: in RPY (degree) ...
```

上面是字段示意，不是实测数值。Translation 表示相机原点相对底盘的位置，不是画面中物体的位置。Rotation 描述相机与底盘坐标轴的朝向差异；相机 optical 轴向和底盘轴向不同，所以旋转通常不全为零。

观察几次输出后按 Ctrl+C，只停止查询。若一直等待或报告缺少 frame，保存错误信息；先核对仿真、source 环境、实际 frame 名和 /tf、/tf_static 发布情况。

本操作不发布运动指令。当前文档已核对工具源码及本机命令环境，实际 TF 连通性以本次运行输出为准。

### 本轮只回答两个问题

1. Translation 是相机相对底盘的位置，还是被看到的物体相对底盘的位置？
2. 相机固定在底盘上，机器人行进时，这组相机到 base_link 的变换应基本不变还是跟着里程变化？

### 2026-11-09 用户输出与解释

用户按操作 A 提交的终端截图已归档至 results/m1_sensor_check/user-camera-tf-2026-11-09.png；来源、SHA-256 和截图转录见同名 .source.json。截图未包含输入命令，坐标系配对依据此前的查询步骤与用户反馈上下文，数值仅保留画面显示的三位小数。

```text
Translation: [-0.037, 0.000, 0.186] 米
Quaternion (xyzw): [-0.500, 0.500, -0.500, 0.500]
RPY (degree): [-90.000, -0.000, -90.000]
```

按底盘 X 前、Y 左、Z 上的约定，相机光学原点在底盘原点后方约 3.7 厘米、横向约零、上方约 18.6 厘米。这里的高度相对于 base_link 原点；不能直接当成离地高度。

该旋转矩阵的三列分别给出相机 X、Y、Z 轴在底盘中的方向：

| 相机轴 | 在底盘中的方向向量 | 含义 |
| --- | --- | --- |
| X | [0, -1, 0] | 底盘右侧 |
| Y | [0, 0, -1] | 底盘下方 |
| Z | [1, 0, 0] | 底盘前方 |

因此，这两个 -90° 可以用来解释坐标轴定义的朝向差异，不能只看 RPY 数值就断定摄像头斜着安装。按截图显示精度，坐标变换可写为：

```text
X_base =  Z_camera - 0.037
Y_base = -X_camera
Z_base = -Y_camera + 0.186
```

例如人为取一个位于相机光轴上的点 [0, 0, 3.000] 米，换到 base_link 后约为 [2.963, 0, 0.186] 米。这是由截图变换计算的示例点，不是本次检测到的物体或地图坐标。实际像素反投影和深度几何对齐仍待后续课程验证。

用户已正确解释 Translation 及固定安装时相对关系不变。截图有重复输出，但没有机器人运动前后的记录，因此尚不把“不变”的正确回答等同于运动实验验证。旋转解释本轮已补充，理解程度后续继续确认。

截图的 At time 0.0 可以出现在全静态的 TF 链查询中；它单独不能说明仿真时间停止，也不能替代 /clock 验收。参见 [Humble TF 时间查询实现](https://raw.githubusercontent.com/ros2/geometry2/humble/tf2/src/buffer_core.cpp)。

## 五 操作 B 认识里程计

保持仿真运行，先按 Ctrl+C 结束上一项 TF 查询，在新终端或同一终端准备环境后执行：

```bash
cd '/home/hao/Documents/ChatGPT/自主移动机器人综合设计大项目/task4_ws'
source sim_env.sh
ros2 topic echo --once --no-arr --qos-reliability best_effort /odom
ros2 run tf2_ros tf2_echo odom base_link --ros-args -p use_sim_time:=true
```

topic echo 只显示一条里程计消息，--no-arr 隐去协方差等数组字段以便阅读；tf2_echo 持续查询坐标变换，观察几组后按 Ctrl+C。两者需要分别检查。本轮先保持机器人静止，检查接收和坐标关系，不发送运动命令；运动前后变化留到后续实践。

Odometry 消息中的 header.frame_id 指定 pose 所属坐标系，child_frame_id 指定被描述的底盘参考系，twist 在 child_frame_id 中表达。position 是位置，orientation 通常以四元数给出，不能把四元数四个分量直接当欧拉角。

里程计是位置、朝向和速度的估计；本机仿真的生成方式与实物底盘内部算法可能不同。可以先把 odom 想成固定在场地中的一把局部尺子，底盘相对它的位姿会随机器人运动改变。其原点和初始朝向由实现决定，不保证机器人初始坐标为零，也不保证等于 Gazebo 世界坐标。长期运行还可能漂移；后续建图定位再引入 map。

| 里程计字段 | 本轮如何理解 |
| --- | --- |
| header.frame_id | pose 使用的参考坐标系，需以实际输出为准 |
| child_frame_id | 被描述的机器人参考系，需以实际输出为准 |
| pose.pose.position | 该机器人参考系原点的位置，单位米 |
| pose.pose.orientation | 朝向四元数，四个数不能直接当角度 |
| twist.twist.linear.x | 在 child_frame_id 中表达的 X 方向线速度，单位米/秒 |
| twist.twist.angular.z | 在 child_frame_id 中表达的绕 Z 轴角速度，单位弧度/秒 |

存在 /odom 消息不自动保证 odom 与 base_link 的 TF 连通。child_frame_id 若是 base_footprint，先记录实际名字，再检查到 base_link 的中间关系；不要擅自改消息来凑名字。

反馈时提供一条 /odom 输出与一组 odom 到 base_link 的 TF；若等待或报错则提供完整错误。理解题：机器人运动时，底盘相对 odom 的位姿为什么会变化，而相机相对底盘的安装变换仍基本不变？

## 六 当前操作 C 认识激光

逐步讲解和本轮反馈要求见 [02C 激光雷达与 LaserScan](02C_激光雷达与LaserScan.md)。当前先读取元信息和接收频率，下一轮实现订阅节点。

```bash
ros2 topic echo --once --no-arr --qos-reliability best_effort /scan
ros2 topic hz /scan
```

hz 持续运行，观察数秒后按 Ctrl+C。它测量接收到消息的频率，可能受订阅和电脑负载影响。

LaserScan 的 ranges 是按角度排列的距离数组，单位为米；angle_min 是起始角，angle_increment 是相邻束角度间隔，单位为弧度。第 i 束角度为 angle_min+i×angle_increment。距离应结合 range_min、range_max 和无效值判断。

零角方向是雷达自身坐标系的 X 方向，不保证等于机器人正前方；还需要雷达的安装 TF。仅根据数组下标判断前方会受到安装方向影响。

## 八 T1.2 运动案例

2026-11-20 的 Gazebo 实测中，先出坞并停稳，再按 0.10 m/s 的指令直行约 2 仿真秒。速度乘时间给出预计距离 0.20 m，里程计测得沿车头方向前进 0.19950 m。表达这三类信息的是 `/cmd_vel`、`/odom` 和 TF。

| 信息 | 本轮怎么看 |
| --- | --- |
| `/cmd_vel` | 给机器人要执行的速度。线速度为 0.10 m/s，表示朝底盘 X 正方向每秒走 0.10 m。 |
| `/odom` | 报告机器人在里程计坐标系里的位置和朝向。直行前后 `x` 从 −0.353 m 变成 −0.549 m。 |
| TF | 描述两个坐标系怎样换算。 `odom→base_link` 随车移动而改变，`base_link→相机` 描述固定安装位置和朝向。 |

为什么前进时 `x` 会变小？出坞后车头朝向约 −169°，几乎指向里程计 X 轴的负方向。向车头前方开就是沿底盘的正 X 方向走，在 `odom` 里却主要表现为 `x` 减小。脚本会用出发时的车头方向来计算“向前走了多少”。

雷达也提供了另一项观察。先用安装 TF 把回波换算到车身方向，车头前方的距离从约 4.654 m 降到 4.454 m，和里程计记录的前进量接近。随后左转 89.47°，相机和雷达跟着车身转，安装关系保持一致。建图时会用到这种组合，把扫描点根据采集时刻的姿态摆到统一坐标系里。

可以先想一个问题。里程计位置变化时，一台固定在底盘上的相机相对底盘的位置是否改变？试着分别用 `odom` 和 `base_link` 说明。
