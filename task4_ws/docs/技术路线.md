# 任务四技术路线

制定日期为 2026-11-07，技术选型于 2026-11-20 复核。本文说明模块方案和选型依据，任务卡、展示安排和降级条件见 [任务四开发与验收路线](任务四开发与验收路线.md)。项目阶段以 [实际状态与证据](../PROJECT_STATUS.md) 为准。

## 开发平台和首版范围

以本机现有 Ubuntu 22.04、ROS 2 Humble、TurtleBot4 Lite 和 Gazebo Fortress 作为首步验证平台。该决定用于开发验证，不代表教师已经认可型号替换。任务书为 TurtleBot2，教程为 TurtleBot3；应在正式多房间场景制作前核实型号要求。上层业务依赖标准 ROS 数据和 TF，降低更换底盘的影响。

首版采用静态物品、预先保存的二维地图、命名房间、多观察点搜索，以及预训练视觉模型。先从瓶子、杯子、椅子中选择实际仿真图像识别效果较好的类别，再扩展。COCO 的 bottle 类不等同于识别可乐品牌。

业务流程为：语音识别与关键词解析 → 任务管理 → 导航到房间 → 执行观察点搜索 → 图像检测与地图定位 → 去重和编号 → 汇总计数并保存标注地图。

## 模块实现方案

| 模块 | 首版方案 | 核心验证 |
| --- | --- | --- |
| 仿真与传感器 | 现有 Fortress/TurtleBot4 Lite；RGB、深度、CameraInfo、激光、里程计、TF | 先确认消息有实际数据，记录编码、单位、坐标系和时间 |
| 场景与地图 | 先用本地 maze 做传感器验证；正式制作含客厅、厨房、卧室及家具的项目场景；键盘遥控配合 SLAM Toolbox 建图 | 地图可保存、重新加载，并与场景对应 |
| 定位与导航 | AMCL 定位、Nav2 导航；全局规划首选 NavFn 的 A*，局部避障沿用 TB4 参数；任务端复用异步 NavigateToPose 客户端 | 运行时核对规划器和 use_astar，验证接受、到达、失败、取消和超时 |
| 物体检测 | Python 节点调用轻量预训练 YOLO，首选 YOLOv8n 做可行性验证 | 先在实际仿真截图中验证，再固定依赖和权重版本 |
| 地图定位 | 对齐的 RGB/深度和对应内参，目标区域有效深度的稳健估计，观测时刻 TF 转到 map | 同一目标从多个位置观测，记录位置误差；无效深度不生成有效坐标 |
| 去重与编号 | 类别和空间位置关联，多次观测确认，单次观测与记录一对一匹配 | 重访不新增编号，相邻物体不被错误合并；阈值根据实测误差确定 |
| 房间搜索 | 预设观察位置和朝向，按实测识别距离、遮挡与门洞视野校核覆盖；逐点到达，停下扫描 | 首次检测后继续搜索；记录每个观察位姿、有效帧和未完成原因 |
| 语音与任务 | 百度短语音或经实测的离线中文 ASR，规则提取房间和类别；底层 ASR 与业务节点解耦，文字输入复用解析和消息协议 | 先实测一句中文指令，最终验收真实语音触发的整链 |
| 标注与保存 | 保存 JSON 清单、原始地图标识和带编号的叠加地图图像；RViz MarkerArray 可后续增加 | 标记、清单和总数一致，重新打开可查，已知非零场景的计数另与独立真值比较 |

首版主要自主开发任务流程、观察点搜索、物体地图定位、空间关联、编号和结果保存。复用的建图、导航和检测组件需要理解输入输出、调参依据和失败条件。

## 数据怎样从相机进入最终清单

1. **建立统一参考。** 键盘遥控时，SLAM Toolbox 用激光、里程计与 TF 生成占据栅格。保存 YAML/PGM 后重启，用 AMCL 在这张地图上定位。房间边界、入口、观察位姿、物品坐标与地图标注共同使用这份地图及其版本。
2. **在有效视野内取观测。** 预设房间观察点，Nav2 确认到达后等待底盘稳定，核对实际位置和朝向，再开启采集窗口。结合检测实测的距离范围和家具遮挡安排观察位姿。空检测帧也要来自有效的 RGB-D、TF 和成功的推理，感知中断须反馈给任务状态机。
3. **从像素换算到地图。** 对齐的 RGB 提供候选框，深度提供光轴方向的米制 Z，对应内参给出 `X=(u-cx)Z/fx`、`Y=(v-cy)Z/fy`。从框内多个前景像素估计一个可见表面位置，再用采集时刻的 TF 把相机系位置转到 `map`。同一物体从至少三个位置采样，分别记录跨视角偏差和有效观测率。表面点随视角变化，使用实例掩膜前先检验框内深度的效果。
4. **按任务关联物品。** 只接受目标类别、目标房间和当前观察窗口内的有效地图点。每批观测一对一匹配，待确认对象经多次独立帧验证后分配稳定编号。门限根据跨视角重访偏差和最近同类物品间距确定。若两者给不出可分开的门限，优先改善定位或摆放，再记录歧义。简单贪心匹配可以作为基线，近邻测试出现可匹配目标被遗漏时，改用门限内优先最大匹配数、再最小总距离的全局分配。
5. **检查正确性与输出。** 在目标房间完成观察计划、感知有效且结果通过读回核对后，才打印完成和总数。用独立的空房、非零、重访场景核对计数。位置评估先独立配准 Gazebo `world` 和 SLAM `map`，说明物品参考点和可见表面点的差异，再报告误差。

### 选型何时调整

- **首版组合。** TB4/Fortress → SLAM Toolbox 与 NavFn → YOLOv8n 与对齐深度 → 任务内空间关联 → 标注地图。ASR 在同一业务链之前提供结构化指令。本机先实测一个目标类别和一个语音后端。
- **部署备选。** 如果 Python 感知环境和 Humble 依赖冲突，先尝试把推理与 ROS 数据处理分到不同进程，或者试 `yolo_ros` 的 C++/ONNX 管线。用相同 RGB-D 帧比较检测、三维坐标和有效帧率，保留任务管理、房间和结果格式。
- **三维扩展。** 如果后续需要稠密三维环境图，先用 RTAB-Map 验证 RGB-D 和导航所需二维地图。只有类别字典无法覆盖实际任务时，再试开放词汇检测和场景图。两者分别验证，便于测量新增依赖和资源开销。
- **模型与摆放。** 先在现有仿真里放一个候选目标模型，采不同距离和角度的真实图像。检测分支效果达标后，再冻结正式房间内的同类目标、光照和摆放。若框内背景导致跨视角偏差，先试分割或更稳健的深度取样；部署或实时性不满足时再评估 ONNX 方案。
- **语音。** 优先跑通一个后端。预检用同一段真实录音，记录关键词解析结果及“录音结束到任务发布”延迟。最终用两种说法覆盖三房间，检验识别和拒识；课程正式语音验收使用实测通过的语音后端。
- **书面证据。** 记录每个候选的仓库、适用分支及接口边界。实际引入时记录固定版本、许可和 SHA-256，再进行本机运行验收。本次 GitHub 调研属于选型依据。

## 阶段和检查点

M0 工作区 → M1 仿真与传感器 → M2 场景建图与导航 → M3 单物体地图定位 → M4 去重计数 → M5 语音整链 → M6 评估展示。M1 中先检查 `odom→base_link→传感器`，建图定位后检查 `map→odom`。计划、并行条件和时间安排统一见 [开发与验收路线](任务四开发与验收路线.md)。

## 建议分工

- A：仿真、传感器、场景、SLAM、AMCL、Nav2。
- B：检测、RGB/深度对齐、时间同步、相机内参和 TF 地图定位。
- C：语音、任务管理、搜索调度、去重编号、标注保存。
- 全组共同确定接口，测试数据与报告据实际贡献记录。用户当前优先跟进 M1，结合实际话题学习节点、消息与发布订阅。

## 评估方案

按 0、1、多个目标分别测试；加入重访、近邻、遮挡、目标位于相邻房间、观察点不可达、传感器缺失和取消场景。记录计数误差、重复计数、漏检、位置误差、耗时和搜索完成情况。仿真真值单独用于评估，任务结果由传感器数据生成。

## 2026-11-09 学习与实现的推进方式

- 以 docs/学习现状与算法实施安排.md 衔接用户逐步学习：每个模块解释最小原理、运行观察、改代码/参数并验证，不等待全部理论课完成。
- 当前先读 /scan，再写只读激光订阅与数据处理节点。SLAM 的建图入口按激光、基础 TF、时间与运动控制依赖验收；RGB/深度几何对齐须在三维目标定位前通过，可与建图并行。
- 复用组件与项目算法分开学习：SLAM/定位/导航/检测先运行并理解配置；目标地图坐标、关联编号、搜索状态机与结果保存重点亲手实现。
