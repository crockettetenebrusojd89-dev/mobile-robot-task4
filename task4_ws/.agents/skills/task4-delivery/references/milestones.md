# 阶段与验收

以工作区 `docs/技术路线.md` 的 M0—M6 为准，详细教师要求见 `docs/任务要求与验收.md`。本表补充实现顺序和检查证据，不新增教师评分项。

| 阶段 | 进入与实现重点 | 能支持通过结论的证据 |
| --- | --- | --- |
| M0 工作区 | 包结构、环境与构建入口 | 构建退出码、已安装入口实际输出与配置发现 |
| M1 仿真与传感器 | 仿真启动；RGB、深度、CameraInfo、scan、odom、clock；基础 TF | 各数据实际样本与时间；相机和激光到 base_link、odom 到 base_link 的 TF；仿真时间与运动前后变化。图像对齐另作几何检查 |
| M2 场景、地图与导航 | 明确平台适用范围；多房间场景；SLAM 保存地图；AMCL/Nav2；房间配置 | 原始地图及重新加载；实际地图标定的房间与观察点；到达、失败、取消的 Action 结果 |
| M3 单物体地图定位 | 已验证对齐的 RGB-D、内参、观测时刻 TF 与可用检测器 | 实际场景检测；同一目标至少三个观察位置的地图坐标、有效深度比例、误差与失败记录 |
| M4 去重计数 | 持久清单、确认规则、同批一对一关联 | 重访不增计数、相邻同类可区分、漏检/误检和无效观测的独立案例 |
| M5 完整任务 | 语音输入、解析、导航、全部计划观察点、汇总与保存 | 一次完整 task_id 链路；数量/编号/标记一致；零目标、失败、传感器缺失、取消行为 |
| M6 评估与展示 | 以实际实验准备视频、PPT、报告与个人贡献 | 可追溯实验目录、计数/定位误差、耗时、失败案例，展示文件与报告引用一致 |

按依赖推进：

- 激光、基础 TF、时间和运动链路满足后可进入 SLAM；不要把尚未完成的图像对齐当作建图的前置条件。
- 实际仿真截图的检测可行性可以提前验证，尽早发现目标模型外观和检测类别不匹配。
- 状态机、去重纯函数和结果读写可以用明确标注的离线输入先开发；整机通过仍需实际感知和导航。
- `rooms.example.yaml` 的 `calibrated: false` 和空坐标不是可执行导航计划；`frames_topics.yaml` 是项目配置草案，不能直接当成 ROS 参数文件传入节点。

## 每轮验收如何落地

先写出本轮要证明的行为和失败条件，再选择最小检查。例如改关联算法时检查“同帧两目标不会占用同一个物品记录”，而不是只检查函数返回了一个列表。

可用现有项目工具完成的检查优先复用：

| 变更 | 检查选择 |
| --- | --- |
| 文档、skill、来源元数据 | frontmatter/YAML/JSON、相对链接、引用文件、模板残留；核对入口确实引用新文件 |
| 激光纯计算 | `python3 -m pytest src/task4_bringup/test/test_scan_math.py`，仅在相关逻辑有变或需要复核时执行 |
| 包依赖、入口、安装配置 | `bash build.sh`，再在本项目环境检查对应安装入口 |
| RGB-D 与基础 TF | 复用 `scripts/check_rgbd.py` 和已有 M1 操作说明；实测报告分开记录数据接收、时间、几何条件 |
| Nav2、完整搜索与计数 | 实际仿真运行，读取最终 Action 状态、观察点执行情况和持久结果；离线测试不能替代 |

每次结果目录按需要保存命令与退出码、配置/源码版本、输入标识、日志和输出文件。不要重用目录覆盖过去的失败或成功证据。

## 面向交付的代表性场景

按模块选择相关场景，不要求文档变更也运行整机：空房间、单目标、多个目标、重访、相邻同类、遮挡/漏检、相邻房间可见目标、不可达观察点、深度或 TF 缺失、搜索中取消。

报告分别回答：计划执行了多少、感知是否有效、确认了多少物品、与独立真值差多少、耗时多久、为何失败。计划观察点全部执行是当前首版的完成定义，仍需评价视野和遮挡，不宣称数学意义上已穷尽房间内所有物品。
