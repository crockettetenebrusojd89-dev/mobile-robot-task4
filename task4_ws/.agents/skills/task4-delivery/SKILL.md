# 任务四项目开发与验收

交付链路：键盘建图并命名房间 → 语音解析房间和类别 → 导航 → 多观察点搜索 → 检测与地图定位 → 去重编号 → 汇总并保存标注地图。教师要求以项目任务书为准，工程建议不能升级为课程要求。

本 skill 位于 `task4_ws/.agents/skills/task4-delivery/`，向上三级是工作区 `task4_ws`，以下项目路径均相对于它。不要依赖项目总目录的中文名称或历史迁移路径。

## 把一项工作做成可验收的交付

1. **确定一个可观察的结果。** 例如“查询激光到 base_link 的 TF 并保存时间与 frame”，或“重复观察同一目标不新增编号”。指出依赖、当前缺口和证据保存位置，避免把一个模块扩写成整套系统重构。
2. **沿现有结构实现。** 先看 `src/task4_bringup/`、`scripts/` 和配置，再决定增量修改。纯算法与 ROS 通信分离，沿用 `scan_math.py` / `scan_reader.py` 的模式；仅在模块边界需要时增加包或自定义消息。
3. **按声明选择验证。** 纯文档检查链接和格式；数学/关联逻辑检查真实边界与行为；包或入口变更用 `bash build.sh` 和安装入口检查；话题、TF、导航及整机效果需要实际运行记录。已有检查只有在输入、代码和环境仍适用时才可引用，并标明原日期。无需为文档修改重建 ROS 包。
4. **检查原始结果。** 记录命令、退出码、输入和环境；区分离线构造数据、助手实测、用户截图与用户回答。失败结果同样保留。只有证据覆盖的能力才能标记通过，静态参数、包发现或构建成功不能替代运行验收。
5. **保存并更新。** 实验放入独立的 `results/<主题>/<日期或运行标识>/`。更新 `PROJECT_STATUS.md`，向 `WORKLOG.md` 追加日期、变更、实际检查、证据和下一步；涉及教学再更新 `docs/学习进度.md`。最终说明交付、验证、剩余缺口和下一项依赖。

## 项目决策约束

- 采用现有 Python / ROS 2 Humble 路线。TurtleBot4 Lite/Fortress 是当前开发验证平台；教师对任务书 TurtleBot2 型号的最终要求仍须核实。缺少型号认可时推进标准接口、离线逻辑和现有平台验证，并明确适用范围。
- 使用 `env.sh`、`sim_env.sh`、`start_sim.sh`、`build.sh` 等本项目入口。系统 ROS、相邻实验和 `migration_archive/` 不作为活动修改目标。教师原件不改写。
- 传感器观测保留采集时间与 frame；三维定位使用观测时刻的 TF。仿真真值只进入独立评估，不进入业务计数。
- 搜索未完成和已完成后的零目标分别表达。视频跟踪 ID 不能直接当作持久物品编号，首次检测到目标后仍须继续搜索。
- 引入源码、模型或权重时记录来源、固定版本、SHA-256 和实际许可证；查阅过某个仓库不等于已安装或验证其组件。本次 skill 的来源锁定仅表示阅读依据。

## 配合当前学习方式

用户 Python 基础较弱，按《学习进度》接续当前课次。把当前真实代码的一小段与一项数据现象连起来，必要时补普通 Python 例子，再用少量手算或解释确认。明确标注教学假设与实测数据。

分别记录“代码已准备”“助手运行”“用户复现”“理解已反馈”“独立修改已验证”。用户选择跳过的练习保留为跳过；未回答的题保留待反馈。用户要求继续时可以推进讲解，不补写通过结论。教学节奏与工程依赖分别判断：SLAM 不必等待 RGB-D 几何对齐，但物体三维定位必须先完成对齐验证。
